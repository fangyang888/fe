# 组件图例与代码检索实施计划

首版要验证的问题是：查询输入固定为同一份 Pixso JSON，给组件索引加入图例描述，能否让前端认可的组件排得更靠前？图例可以来自组件文档或示例截图，只在入库时读取。首版用视觉模型把图例转成可检索的文字，让图例、代码和 Pixso JSON 可以使用同一套文本 embedding。

## 现有代码怎么用

| 能力 | 仓库依据 | 实施决定 |
| --- | --- | --- |
| 文本 embedding | [rag_learning 的 embedding_search.py](../../../projects/rag_learning/llama/milvus_course/embedding_search.py) 使用 OpenAILikeEmbedding，区分批量入库与查询，按模型指纹隔离集合 | 复用其 EDU_EMBED_BASE_URL、EDU_EMBED_MODEL、EDU_EMBED_API_KEY 配置、维度检查和指纹算法；组件集合使用独立名称 |
| Milvus | [milvus_basics.py](../../../projects/rag_learning/llama/milvus_course/milvus_basics.py) 提供连接、建表和 COSINE 检索示例 | 新建组件 schema。课程的 PyMilvus、Milvus Lite 和 embedding 集成是脚本级依赖，组件图需在自己的运行环境显式声明 |
| 聊天与读图 | [聊天模型工厂](../core/create_model.py) 提供聊天入口；当前仅核对了配置与源码 | 先用一张已知布局的小图验证端点能否读取图像。支持时沿用；否则允许指定视觉模型。没有可用视觉模型时仍可跑代码基线，已写好的图例说明也可作为有来源的输入 |
| 流程编排 | [StateGraph 示例](../graphs/demo/demo_loop_graph.py) | 两张独立的图：组件库更新触发入库图，每次设计稿匹配触发查询图。凭证核验是查询图的结束阶段 |

## 第一阶段 · 组件入库

`读取包或文档 → 建组件目录 → 切分代码与文档 → 描述图例 → 生成向量 → 校验并发布索引`

**本机目录入口**。用户只需给一个本机可读的路径，可以是组件库源码目录、已安装的包目录（如 `/path/to/app/node_modules/@scope/ui`），或只有文档和图例的目录。相对路径以启动目录为基准；组件、文档和图例分开放时，可另给文档目录或图例目录。入库图可以独立运行，Pixso JSON 在查询阶段再提供。

扫描范围限定在指定材料内。优先识别包清单、公开入口和文档对示例或图片的显式引用，避免把项目的依赖树一起入库。能读取包版本时记入清单，只有文档时使用内容快照标识。入库完成后返回库版本或快照、构建 ID、实际写入的组件数和片段数、成功关联的图例数，以及跳过文件与原因；抽取一个组件回读 Milvus 记录并核对本地来源。

- 接收指定版本的 npm 包目录，或本地文档快照。包从公开导出追到声明与用例；文档按组件页、标题、Props 表和代码块解析。由组件名、导入路径和版本确定组件身份。图例绑定到具体组件和用例变体；页面里有多张图时记录其标题和出处，关联不明确的图留待核对。
- 按用途、同组 Props、完整示例、限制说明切片。每片保存组件 ID、片段类型、原文、来源文件或 URL、符号或标题锚点及快照哈希，给凭证核验回读。
- 为每个示例变体生成可检索摘要。摘要含组件用途、关键 API 和代码可知的特征；有图例时补充排列、外形、状态标记等可见信息，并关联图片引用。例如 Tabs 可补充「三个文本项横排，活动项下方有短线」。图片无法确定的行为留给 API 与用例判断。
- 产出两组可比较的摘要，保留相同的组件、变体和记录数，仅改变是否拼入图例描述。证据切片公用。键包含构建 ID、组件 ID、变体或片段 ID 和索引模式；重复导入同一批材料可安全重试。只在记录数、向量维度、来源回读均通过后发布构建。

## 第二阶段 · Pixso 查询

`读取 Pixso JSON → 按功能分区 → 生成区域描述 → Milvus 过滤检索 → 按组件聚合`

- 提供两种输入：Pixso 图层链接经 MCP 适配器读取结构，或直接回放保存的 JSON。二者进入同一归一化节点，保留节点 ID、父子关系、文本、边界和响应中实际存在的样式。回放用于调试和对照实验。
- 分区节点从容器、重复结构、相对位置生成筛选区、表格、分页等区域。每条观察关联节点 ID。查询描述使用与图例一致的词汇；JSON 只给出文字时跳过未知样式。
- 固定模型指纹、组件库、版本与构建，按索引模式在 Milvus 检索摘要。每区先取最多 20 个片段，按组件 ID 合并变体，保留前三个不同组件及其最佳变体。窗口可在真实库上校准。

## 第三阶段 · 推荐凭证

`读取候选原始材料 → 按需求核验 → 保存已匹配的区域、推荐理由与可用的图层截图`

以标签区为例，报告将三类记录放在一起：

| 记录 | 验收时要能看到什么 |
| --- | --- |
| 设计依据 | 指定 Pixso 节点呈现横排文本，活动项下方有短线。可由报告回到节点或快照位置 |
| 外观依据 | 对应版本的候选组件及其图例变体表现出相同特征。可打开原图对照 |
| 能力依据 | 如果需求明确要求受控切换，引用该版本的选中值 Prop、切换事件或用例原文。若设计稿只展示静态选中态，报告只断言这一点 |

程序核对设计节点、构建 ID、快照与引文。每个匹配区域输出一个组件、理由、图层链接和来源。在线查询附上可获取的图层截图。所有区域处理完毕后自动保存报告。

## 编码顺序和交付验收

1. 在本目录实现数据结构、组件入库图和查询图，提供 ingest 与 match 入口。先用 Tabs 与 Segmented 两个文案相近的组件和固定 Pixso JSON 打通入库、检索、凭证回读与保存。
2. 接入真实包或文档、视觉模型、Pixso MCP。对照同一设计稿的 MCP 输入与 JSON 回放，检查区域和引用一致；用无图例、旧版本、缺 Props、零命中样本检查降级与空结果。
3. 用同一批前端标注区域评估。保留纯代码索引作为原始基线，再对比「相同的代码及文档摘要」和「相同摘要加图例描述」；三组固定查询、候选库和检索参数。报告正确组件排第一的比例、进入前三的比例、按区域列出的升降案例，以及推荐依据能否回读。用真实标注结果决定默认检索模式。

联调材料是一份目标组件包或文档入口、能对应组件的图例，以及一个真实 Pixso 节点链接或导出的 JSON。第一阶段可先用示例材料启动。
