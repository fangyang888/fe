# 第 01 章：认识 RAG 与数据边界

## 本章目标

学完后你应该能解释：RAG 是什么、它不是什么，以及商城客服中的哪些问题应该使用 RAG。

---

## 一、RAG 解决什么问题

大模型可能知道通用知识，但不知道你公司刚发布的退货政策、配送规则或商品说明书。直接让模型回答时，它可能生成一段合理但不符合真实规定的内容。

RAG 的基本流程是：

```text
用户问题
→ 检索可信资料
→ 得到少量相关证据
→ 问题和证据一起交给模型
→ 根据证据回答并展示来源
```

RAG 的全称是 Retrieval-Augmented Generation，即“检索增强生成”。

必须记住：

```text
RAG 不是训练或微调模型
RAG 不是聊天记录
RAG 不是让模型直接查询所有数据库
RAG 不能天然消除幻觉
```

---

## 二、RAG、微调、Tool 和记忆的区别

| 能力 | 解决的问题 | 商城示例 |
| --- | --- | --- |
| RAG | 查阅可更新的非结构化知识 | 退货政策、FAQ、说明书 |
| 微调 | 改变模型的行为、语气或特定模式 | 固定客服表达风格 |
| 业务 Tool | 查询实时且确定的业务事实 | 库存、价格、订单状态 |
| 会话记忆 | 理解当前对话已经发生的内容 | “刚才说的那款耳机” |

一个问题可能同时需要多个能力：

```text
用户：我的订单现在还能退吗？

OrderService → 购买时间、订单状态、商品类型
RAG          → 当前退货政策、例外条款
业务规则代码 → 确定是否满足申请条件
模型          → 解释判断和引用政策
```

最终资格判断不能交给向量相似度或模型自由推理。

---

## 三、四步判断法

拿到一个需求时依次判断：

1. 答案是否来自文档、FAQ、手册或规则？是则考虑 RAG。
2. 答案是否实时变化并需要确定性？是则使用业务 Service/Tool。
3. 答案是否只存在于当前对话？是则使用会话上下文。
4. 是否需要同时组合政策与个人业务数据？是则使用受控组合流程。

### 适合 RAG

- 售后政策。
- 配送说明。
- 优惠券规则说明。
- 商品使用手册。
- 常见故障排查。
- 客服操作指南。

### 不适合只用 RAG

- 当前库存和价格。
- 用户自己的订单和物流。
- 余额、优惠券数量和退款进度。
- 需要强鉴权的个人信息。
- 退款、取消订单等写操作。

## 四、当前项目推荐架构

```text
AgentService
├── 知识政策问题 → KnowledgeAnswerService（2-Step RAG）
├── 商品问题     → ProductCustomerService
├── 订单问题     → 鉴权后的 Order Tool/Service
├── 普通问题     → 当前 Agent
└── 混合问题     → 受控工作流组合 RAG 和业务 Service
```

第一版不要把 Retriever 注册成 Agent 可以任意调用的 Tool。固定流程更容易定位问题、控制延迟和验证引用。

## 五、本章练习

建立一张包含至少 30 个真实客服问题的表，为每条标注：

```ts
type QuestionRoute =
  | 'rag'
  | 'business_tool'
  | 'conversation_memory'
  | 'rag_and_tool'
  | 'direct_answer';
```

至少包含：

- 8 个政策或说明书问题。
- 8 个订单、库存或价格问题。
- 4 个多轮指代问题。
- 5 个混合问题。
- 5 个不需要检索的普通问题。

---

## 六、自测问题

1. RAG 和微调的区别是什么？
2. 为什么库存不能只依赖向量库？
3. 为什么“我的订单能否退货”不能只让模型判断？
4. 聊天历史和企业知识库分别解决什么问题？
5. 什么是 2-Step RAG？

## 验收标准

- 30 个问题中至少 27 个路由合理。
- 能解释每个问题的事实来源。
- 不把实时数据、权限判断或写操作交给 RAG。
