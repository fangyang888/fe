# 第 11 章：多轮查询改写与上下文工程

## 本章目标

让 RAG 能正确处理“它”“那个政策”“多久能到账”等多轮指代，并在有限 Token 预算内组织高质量证据。

---

## 一、聊天消息不是最好的检索 Query

对话：

```text
用户：我买了一副降噪耳机。
助手：你想了解使用还是售后？
用户：拆开以后它还能退吗？
```

最后一句直接检索时，“它”没有明确对象。应改写成独立问题：

```text
已拆封的降噪耳机是否符合退货政策？
```

查询改写的目标是补足指代和检索关键词，不是回答问题。

---

## 二、优先使用确定性业务 State

当前项目已有对话状态和实体抽取思路。查询改写时优先使用已验证状态：

```text
selectedProductId
selectedProductName
orderNo
categoryName
conversationSummary
```

不要每次把全部历史消息无限传给改写模型，也不要让模型从很长历史中自由猜测关键实体。

---

## 三、结构化改写输出

```ts
type QueryRewrite = {
  standaloneQuery: string;
  requiresClarification: boolean;
  clarificationQuestion: string | null;
  usedEntityKeys: string[];
};
```

改写服务可以决定：

- 查询是否已经独立完整。
- 能否从可信 State 补足指代。
- 缺少关键信息时是否先澄清。

它不能决定：

- `tenantId`。
- 用户角色。
- 可以访问哪些文档。
- 是否允许执行退款或订单操作。

这些始终由服务端权限和业务代码决定。

---

## 四、何时使用 Multi-Query 和 Query Decomposition

### Multi-Query

生成多个不同表达来提高召回，例如：

```text
耳机退货条件
音频商品七天无理由限制
已拆封耳机售后规则
```

代价是更多检索、去重和延迟。只在单查询召回确实不足时加入。

### Query Decomposition

把需要多个知识点的问题拆开：

```text
“耳机能不能退，退款多久到账？”
→ 子问题 1：耳机退货条件
→ 子问题 2：退款到账时间
```

它适合明确的多意图或多跳问题，但要限制子查询数量和总耗时。

### HyDE

先生成假设性答案再用于向量检索。它可能提升某些语义召回，也可能把模型猜测带进检索方向。没有评估证明时暂不使用。

---

## 五、Context Selection

检索到候选不表示应该全部交给模型。最终上下文需要考虑：

- 与问题的相关性。
- 来源权威等级。
- 版本和有效期。
- 不同证据之间的覆盖度。
- 重复程度。
- Token 预算。
- 是否包含完整条件和例外。

简单预算：

```text
模型上下文窗口
- 系统指令
- 对话摘要和必要实体
- 用户问题
- 为回答输出预留的 Token
= 可用于证据的预算
```

不要先塞满历史消息，再把剩余空间随意留给 RAG。

---

## 六、证据冲突

冲突处理顺序：

1. 过滤未发布、过期和旧 revision。
2. 比较来源权威等级。
3. 使用业务生效时间。
4. 明确记录仍然存在的冲突。
5. 无法可靠解决时拒答或转人工。

不要让模型根据措辞“看起来更像真的”自由选择。

---

## 七、与聊天持久化的边界

```text
Checkpointer / ConversationService
→ 保存消息、摘要和当前业务实体

Knowledge Search
→ 根据独立查询查企业资料

Answer Service
→ 组合有限对话上下文和检索证据
```

`thread_id` 只是会话标识，不是用户鉴权，也不能替代 tenant 权限过滤。

---

## 八、测试清单

- 独立问题不会被无意义改写。
- “它”能从可信实体状态正确补足。
- 两个可能对象时会澄清而不是猜测。
- 改写输出无法更改 tenantId。
- Query Decomposition 有子查询数量和超时限制。
- 最终上下文遵守 Token 预算。
- 多轮查询仍执行相同权限过滤。

## 验收标准

- 多轮指代问题的检索指标明显可测。
- 查询改写和回答生成是两个可独立测试的步骤。
- 权限不由查询改写决定。
- 最终上下文可解释且未被重复 Chunk 占满。
