# 向量分析 MCP

独立的只读 MCP 服务，供 agent 获取开奖历史、对照两组向量方案、回放32/36码结果和查看学习依据。采用标准 stdio 传输，不占用 HTTP 端口，不修改历史、网页方案或冻结记录。

## 启动

需要 Node.js 20 或以上。首次在本仓库内构建：

```bash
cd vector-analysis-mcp
npm ci
npm run build
LOTTERY_HISTORY_URL=http://127.0.0.1:3000/api/history npm start
```

`npm start` 启动后等待 MCP 客户端通过标准输入调用，不是网页服务器。协议输出使用 stdout，启动日志使用 stderr。

配置可通过客户端的环境变量传入：

- `LOTTERY_HISTORY_URL`：开奖接口完整地址，默认 `http://127.0.0.1:3000/api/history`。本地使用阿里云现有接口时可设置为 `http://47.106.103.79/api/history`；使用域名 HTTPS 时需确认该域名证书与接口可访问。
- `LOTTERY_HISTORY_FILE`：可选，历史 JSON 文件绝对路径。设置后优先读文件，用于离线研究和复现，不访问接口。格式同 `/api/history`：数组，每项包含 `year`、`No`、`n1`～`n7`。

不会自动加载 `.env`。工具调用参数不能更换历史 URL 或文件，只能由启动环境配置。

## 接入客户端

`examples/client-config.json` 是使用 `mcpServers` JSON 格式的客户端配置模板。将 `args` 改为实际绝对路径，并设置数据源。客户端若找不到 Node，可把 `command` 改为 Node 的绝对路径。

不同客户端配置格式可能不同；Codex 的 TOML 模板见 `examples/codex-config.toml`。服务代码本身不会自动注册或改动客户端全局配置；本次已按用户授权通过 `codex mcp add` 将 `vector-analysis` 注册到本机 Codex。

## 工具

| 工具 | 用途 | 参数 |
| --- | --- | --- |
| `get_draw_history` | 已排序的历史开奖及数据指纹 | `limit` 1～2000，默认100 |
| `get_vector_forecast` | 两组方案的下一期号码 | `pick_count` 32或36，默认32 |
| `backtest_vector_models` | 两组方案32/36码的覆盖次数及逐期结果 | `window` 20/50/100；`include_rows` 默认true |
| `explain_vector_forecast` | 相似近邻、候选替换、前100期学习证据 | 无专属参数 |

所有工具都支持 `as_of: {"year":2026,"No":250}`。此参数在解析和学习前先截断数据，仅使用该期及之前的历史。返回的 `through`、`historySha256` 和模型版本用于确认比较时使用的是哪批数据。

模型名：`vectorLearn` = 向量历史学习；`vector` = 原向量间隔近邻。

36码沿用已验证的扩展规则：保留32码，再按当期开奖前的原规则排名补入4个未选号码。每期独立使用此前历史，不能把当前预测回填过去。

## 单独部署

开发时，`npm run build` 从同仓库的 `../src/lib/likely32Lab.ts` 及其依赖生成 `generated/vector/`，不复制另一套算法来修改。前端算法更新后需重新执行此命令。生成目录不提交 Git。

部署运行时，复制本目录下的 `index.js`、`lib/`、`generated/`、`package.json` 和 `package-lock.json`，再执行 `npm ci --omit=dev`。此时无需前端源码或 TypeScript。不要漏传 `generated/`。

目前提供本地进程的 stdio 接口。若要部署阿里云并从其他机器以 URL 连接，还需增加远程 MCP 的 HTTP 传输与访问认证；现有 `npm start` 并不提供远程 MCP 地址。

## 解释结果

每次调用会读取数据源；同一数据指纹可复用一次计算结果，数据修正或新增后重新计算。计算放在线程中，排队执行，避免阻塞 MCP 握手和并发请求。接口超时20秒，计算超时90秒；客户端建议允许120秒调用时间。

回放结果是历史覆盖率，不是下一期命中概率；相似度和学习支持度也不是概率。这些方案已用既有历史探索过，不能把同批数据当成独立验证。工具不自动搜索最优参数，也不保证 agent 或 MCP 能提高命中率。

## Agent 参数与算法调度实验

新增工具：

- `get_scheduled_forecast`：选择 `scheduler` 为 `rolling100`、`recent20`、`context100` 或 `ensemble100`，返回下一期32码、实际选中的算法与参数、学习截止期、候选成绩和选择原因。默认固定为 `rolling100`，不因最新回测结果自动更换默认值。
- `backtest_scheduler`：同时对照四种调度方式与原向量、历史学习、原规则。`window` 支持20/50/100，`include_rows` 默认false。返回近三个窗口、剔除近100期的较早历史和全部有效历史成绩，避免只展示近期最高值。

参数候选集在首次回测前固定为16组：4个现有算法（历史学习、原向量、收益门槛、原规则），以及12组学习参数（窗口50/100 × 支持度0.5/0.6/0.7 × 最多替换2/4码）。每个参数候选先独立产生预测，再读取该期开奖评估全部候选，包括未被选中的方案。

候选准备满100期后，调度器再积累100期有效候选成绩，首次纳入调度统计的是历史第211期。所有对照组使用相同有效目标期。每次选择只读此前100期，不包含待预测期结果。

四种调度规则固定为：

1. `rolling100`：此前100期等权评分，领先当前候选超过2个百分点才切换。
2. `recent20`：同样使用此前100期，成绩权重半衰期20期，切换门槛同上。
3. `context100`：根据候选池分布、近邻平均相似度、候选数量和评分差，给相似历史状态更高权重；不读取目标结果。
4. `ensemble100`：按前100期排名选择最多三组不同的32码候选，等权投票；同票优先历史学习原码，再按号码升序，固定保留32码。

这是可由 Agent 调用的确定性调度算法；不是额外启动一个LLM凭文字猜号码。候选库、切换规则和版本会随结果返回。Agent 可以选择要研究的调度规则，但工具不会修改线上页面或自动发布回测赢家。

运行一轮完整实验（先保存协议，再保存结果）：

```bash
LOTTERY_HISTORY_URL=http://47.106.103.79/api/history \
SCHEDULER_REPORT_PATH=/tmp/vector-scheduler-report.json npm run experiment
```

给 Agent 的调用示例：

> 调用 vector-analysis 的 backtest_scheduler，比较四种调度规则近20/50/100期和较早历史的表现；保留32码，说明是否超过原向量。再调用 get_scheduled_forecast，使用 rolling100 返回下一期号码、参数和截止期。不要只按最新回测最高值宣称提升，不修改原页面。

工具支持的截止期参数仍为 `as_of`，用于复现，不等于前瞻记录。后续真正的独立检验需要在开奖前保存不可回填的预测快照；此MCP当前仍为只读分析服务。

## 候选范围诊断

`diagnose_candidate_pool` 接受 `window: 20 | 50 | 100`（默认100）和可选 `as_of`，返回：

- 16个候选平均有多少组不同预测、多少共同号码、两两重叠多少。
- 原向量命中次数，以及是否至少有一个候选包含特别码。
- 全部候选共同漏中的期号，以及原向量漏中但其他候选命中的期号。

后两项依赖已经发生的特别码，仅用于解释失败原因。`hindsightAnyCandidateHits` 是事后理想选择的覆盖上限，不是可实现的预测成绩，也不能输入当期调度决策。

截至2026-276期的100期诊断：16组参数平均只有4.2组不同号码，每期28个号码所有候选都共有，候选并集为36码；原向量77期命中，任一候选命中81期，全部候选共同漏中19期。因此，仅切换现有候选在这100期最多存在4期事后可挽回空间，并不能保证提前识别这4期。

后续研究应先比较能对49码重新评分的独立候选模型，再检验它是否能在不丢掉原有命中的情况下改善共同漏中。新模型必须使用固定实验规则逐期评估；这段历史已用于分析，不能再称为未见过的独立测试集。

## 号码级学习：重新评分49码

新增 `get_number_forecast` 和 `backtest_number_learner`。前者返回全49码评分、前32码、学习窗口和16项特征权重；后者支持 `window: 20 | 50 | 100`、`include_rows`（默认false），同时对比原向量、历史学习和原规则。两者均支持 `as_of`。

第一版固定协议为 `number-softmax100-v1`，不自动调参：

- 49个号码共享一组16维特征权重，以每期唯一的特别码作为49分类标签，拟合带L2正则的softmax模型。
- 特征包括七码频次5/20/100期、特别码频次20/100期、两类遗漏、上期出现、频次变化、向量近邻支持、100期近邻评分及原三组方案的入选指示。
- 每期将全部49码重新排序取前32，不限制在旧的36码候选并集内，也不限制最多替换4码。
- 拟合只使用此前100个已结算的特征/标签样本；每次从零权重开始，固定12次全批量更新，学习率1、L2系数0.02，不携带更早训练权重。特征按各自当时可见的数据构造。
- 原始频次与遗漏特征最多使用此前100期；沿用的向量特征包含更早的已知历史。因此，“训练100期”不表示所有输入都与更早历史无关。
- 先用100期形成特征，再积累100期训练样本；首个计入统计的目标是历史第201期。所有基线使用同一组有效目标期。
- 先预测，再读取该期特别码形成下期可用样本。返回的softmax分值未经概率校准，不代表真实中奖概率。

回测除了命中率，还返回 `versus` 中相对原方案的救回/损失、旧候选池共同漏中次数及救回次数、平均选入多少旧范围外号码。仅救回更多漏中而损失更多原命中，不算提升。

```bash
LOTTERY_HISTORY_URL=http://47.106.103.79/api/history \
NUMBER_REPORT_PATH=/tmp/number-learning-report.json npm run experiment:numbers
```

脚本先保存 `.protocol.json`，再通过真实MCP客户端调用回测和预测。计算只在调用这两个新工具时运行；旧工具不额外拟合号码模型。此版本未替换网页结果，也未自动发布为默认方案。

首次固定协议回放（截至2026-276期，未据结果调参）：号码学习近20/50/100期分别为13/20、38/50、69/100；同期原向量为16/20、43/50、77/100，历史学习为18/20、40/50、72/100。近100期救回旧候选池共同漏中的13/19期，但相对原向量总计救回14期、损失22期，净少命中8期；全1172个共同有效目标期也未超过原方案。它扩大了号码探索范围，但此次未获得覆盖率提升，不能作为已经改善的模型发布。
